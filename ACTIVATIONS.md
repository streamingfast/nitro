# Arbitrum activations

Scope: every ArbOS version that nitro `v3.12.1` (go-ethereum submodule `5eee8f546e7602b7deeef7909f291bbebc77e233`) knows about. The baseline for comparison is nitro `v3.11.4` (geth `dff2aadcd2e75e33923b13acce6468d847477e79`).

Checked: 2026-10-16.

How the status was checked: we read the ArbOS version from each block header (`mixDigest[16:24]`, as decoded by `types.DeserializeHeaderExtraInformation`). We searched the public RPCs (`arb1.arbitrum.io`, `nova.arbitrum.io`, `sepolia-rollup.arbitrum.io`) for the first block at each version. We also queried the current value of `ArbSys.arbOSVersion()` (which returns 55 + version), `ArbOwnerPublic.getScheduledUpgrade()`, `getCollectTips()`, `getTransactionFilteringFrom()` and `ArbGasInfo.get{,MultiGas}PricingConstraints()`. Dates are block timestamps in UTC. All three chains are at **ArbOS 61** today and have **no upgrade scheduled** (`getScheduledUpgrade() = (0,0)`).

## Code facts

- `params.MaxArbosVersionSupported = MaxDebugArbosVersionSupported = 61` (geth `params/config_arbitrum.go`). This is unchanged from v3.11.4. The `UpgradeArbosVersion` switch in nitro `arbos/arbosState/arbosstate.go` handles 2..61. Any higher version hits `default:` and returns `ErrFatalNodeOutOfDate`. As a result, v3.12.1 cannot run past ArbOS 61, and there is no "next" ArbOS version in this release.
- New in geth 5eee8f546e: `ArbosVersion_Amsterdam = 70` carries a `// TODO make sure that this is the version that should gate Amsterdam fork` comment. `IsAmsterdam` is now gated only on `arbosVersion >= 70`. Before this change it used `AmsterdamTime`, which is nil on Arbitrum, so Amsterdam never activated. Because 70 > 61, all Amsterdam code is **dormant** in v3.12.1. A future nitro release has to raise the max version before it can activate.
- `ArbosVersion_Elara = 60` was added as an alias. `Rules.IsGreaterEqual60` was renamed to `Rules.IsElara`, and `Rules.ChainID` was removed.
- Ethereum fork mapping on Arbitrum (`params/config.go`): Shanghai = ArbOS 11, Cancun = 20, Prague = 40, Osaka = 50, Amsterdam = 70. BPO1..5 and UBT/Verkle stay time-based. Those times are nil on Arbitrum, so they never activate.
- The precompile sets live in `core/vm/contracts.go` `activePrecompiledContracts` and nitro `gethhook/geth-hook.go`:
  - below 30: Berlin
  - 30: Cancun + P256 (0x100)
  - 41: Cancun + P256
  - 50: Osaka, which adds BLS12-381 0x0b-0x11 and the EIP-7823/7883 modexp changes
  - 60: Osaka

  The ArbOS precompiles are also registered per version.

## Notes on risky items

1. **Amsterdam (ArbOS 70) is wired in geth but unreachable in v3.12.1.** It will matter once a future nitro release raises `MaxArbosVersionSupported` and governance schedules it. In geth 5eee8f546e:
   - **EIP-7708 logs** come from three places:
     - `core.Transfer` (`core/evm.go:152`) emits a `Transfer(address,address,uint256)` log from `params.SystemAddress` (0xff..fe) for every non-zero value transfer. This includes the **ArbitrumDepositTx** path in nitro `arbos/tx_processor.go`, which now calls `core.Transfer(..., evm.ChainRules())`.
     - `opSelfdestruct` (`core/vm/instructions.go:990`) emits Transfer or Burn logs.
     - `LogsForBurnAccounts` adds burn logs **after** the root call has exited (`core/state_transition.go:1063`).

     The shared tracer attaches a log emitted with no active call to the root call. It still panics when there is no root call, for example in a system call or a tx without calls. ArbOS transfers made through `util.TransferBalance`/`MintBalance` (fees, escrow, retryable refunds) do **not** emit 7708 logs. Consumers will see value transfers logged inconsistently.
   - **EIP-8037**: gas becomes 2-D. The adapter uses neither `OnGasChange` nor `OnGasChangeV2`, so no hook breaks. However, `OnExit` `gasUsed`, receipt `GasUsed`, and block gas (`ChargeGasAmsterdam`) change meaning. Nitro's `ArbosPrecompileWrapper.RunAdvanced` zeroes the caller's state-gas reservoir. Its comment says this is "only valid below Amsterdam", so the Amsterdam integration is incomplete upstream.
   - **EIP-7928**: `Engine.Finalize` ignores the BAL, and `ProcessParentBlockHash(..., nil)` likewise ("Once ArbOS supports Amsterdam, a real accumulator must be threaded through"). The Firehose header already maps `BlockAccessListHash`. No BAL content goes into the block model.
   - The adapter's `firehose.Rules` has no `IsOsaka`/`IsAmsterdam` field. The shared tracer currently only branches on `IsPrague`, so this is fine today.
2. **Tip collection is live on One and Sepolia, but not as an ArbOS bump.** It changes Firehose content at a block chosen by the chain owner, through `mixDigest[25]` and storage:
   - There is a new REWARD_TRANSACTION_FEE balance change per user tx.
   - GAS_BUY and GAS_REFUND amounts grow.
   - Receipt `EffectiveGasPrice` follows `min(base+tip, cap)`.

   The shared tracer computes `TransactionTrace.gas_price` as `min(tip+baseFee, feeCap)` (`computeEffectiveGasPrice`). That value now matches the chain for user txs on One and Sepolia. It does **not** match on Nova, on any block before the toggle, or for delayed-inbox txs (`CollectTips()` is false there). On those, the actual price is baseFee. This mismatch predates v3.12.1 (the old tracer's `gasPrice()` did the same). `ReceiptData` does not carry `EffectiveGasPrice`, so the tracer cannot tell. Worth a test across block 508190474 on One.
3. **Balance-reason mapping.** `balanceChangeReasonFromChain` in geth `eth/tracers/firehose_adapters.go` handles reasons as follows:
   - Every reason ≥128 (all ArbOS reasons, including `BalanceChangeMultiGasRefund`, mint/burn native token and activation fee) becomes TRANSFER.
   - `BalanceChangeUnspecified` becomes UNKNOWN, which the tracer **drops** (`OnBalanceChange` returns early). Nitro only uses Unspecified in genesis/initialize (`arbos/arbosState/initialize.go`).
   - `BalanceChangeRevert` (15) is **not mapped and would panic**. It is only emitted by the `tracing.WrapWithJournal` wrapper, which Firehose does not use.

   No new balance reason was added between dff2aad and 5eee8f546e. The new `GasChangeAccountCreation` (20) and `NonceChangeSelfdestruct` (7) are not consumed, because the adapter registers `OnNonceChange` v1 and no gas hook.
4. **Behavior change that is not tied to an activation and affects all history (geth merge, not ArbOS).** `hookedStateDB.SelfDestruct`/`SelfDestruct6780` no longer emit hooks. The selfdestruct code change and a new nonce reset to 0 are now emitted in `hookedStateDB.Finalise` (sorted by address, next to the post-selfdestruct burn that was already there), which runs after the root call exits but before `OnTxEnd` (`core/state_processor.go:220`). In Firehose these land in the deferred state and attach to the **root call**, with ordinals after the root call ends. Battlefield's canonical Ethereum snapshots expect this shape. The SUICIDE_WITHDRAW balance change is still emitted at the opcode (`instructions.go`). Expect block diffs against blocks produced with v3.11.4-fh on any tx that selfdestructs.
5. **ArbOS above 61 halts the node.** If governance schedules 62+ (for example 70), v3.12.1-fh exits with `ErrFatalNodeOutOfDate` at the upgrade block. On-chain it stops rather than producing a wrong block. No new Arbitrum tx type exists in 5eee8f546e (types 0-4, 0x64-0x6A, 0x78 are unchanged). `init()` in `eth/tracers/firehose.go` validates unknown types at startup.
